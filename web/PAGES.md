# Private Cloudflare Pages deployment (no Zero Trust)

The Pages version has a single-owner password login. Cloudflare Access, a Zero Trust subscription and a payment card are not needed for this login. There is no registration, invitation flow or email delivery. The existing local/Sites build is unchanged.

## Build and upload

Use Node 24:

```sh
cd web
npm ci
npm run build:pages
node scripts/test-pages.mjs
```

Upload **only `web/dist-pages`** using the Pages dashboard folder upload. For the existing project, use Deployments / Create a new deployment, choose **Production**, and upload the newly generated folder. It includes a single module `_worker.js`, static files and `_routes.json`. Every route invokes the guard; only the login page, its two font files, and installation icons/manifest are available anonymously. Source, database migrations, credentials and image provenance files are not published as static assets.

## Dashboard setup

1. In the `tinydreams` Pages project's production Settings / Bindings (Associações), keep `DB` bound to the existing **tiny-dreams** D1 database. Do not create a replacement database.
2. In production Settings / Variables and Secrets (Variáveis e segredos), add **`OWNER_PASSWORD` as a Secret / encrypted value**, not plain text. Choose a unique password of 16–256 characters, preferably generated by a password manager. Do not send it in chat or put it in the repository.
3. `OWNER_EMAIL`, `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` from the previous Access-based instructions are no longer used and can be removed. The earlier preview-only Access restriction can be disabled in Pages Settings / General / Preview access; do not activate a paid plan. If Access was separately enabled for the production hostname, disable that Access application so visitors reach this login instead.
4. Under runtime Settings, set the translated **Fail open/closed** option to **Fail closed**. This prevents static files from bypassing the guard if the Functions quota is exhausted.
5. Save the settings, then deploy the newly generated `dist-pages` folder to **Production**. Settings changes require a new deployment.
6. Open `https://tinydreams.pages.dev` in a private browser window. You should be redirected to `/login`. Enter the password. Confirm your existing dreams are present, then check a reversible change and reload. Preferences includes **Sair da conta**; logging out revokes that browser's session.

The app creates only two additive authentication tables (`td_auth_sessions` and `td_auth_attempts`) in the bound D1 on first login. It does not alter existing dreams or rewrite ownership. The original app schema must already be up to date; future application migrations still use the existing migration workflow.

## Authentication behavior

- Only a correct password grants a session. Browser-supplied user identity and Cloudflare Access headers are ignored. The authenticated owner maps to the existing `local-preview` records, preserving local D1 data.
- The password remains an encrypted Cloudflare secret at rest, supplied only to the server. It is never embedded in the upload or logged by this implementation. It is submitted over HTTPS and checked with Web Crypto MAC verification. This is a single-owner deployment secret, not a user-password database.
- Sessions use 32 random bytes, an origin-bound HMAC, a hashed token in D1, seven-day expiration, and a host-only `Secure`, `HttpOnly`, `SameSite=Strict` cookie. Logout deletes the server-side session. Changing the password and redeploying invalidates previously signed sessions in the new deployment.
- Login accepts up to five attempts per IP in a fixed fifteen-minute window, counted atomically in D1 across isolates. Expired attempts and sessions are cleaned on login. This is basic per-IP protection; it does not stop a distributed denial-of-service attack or protect against Cloudflare plan quota exhaustion.
- Login, logout and authenticated mutations require an exact same-origin Origin header. Missing/short password, missing DB, failed session checks or unavailable auth storage deny data access. The login page displays a setup/unavailability message when appropriate.
- No password reset email is sent. To recover access, replace `OWNER_PASSWORD` in the dashboard and redeploy. Save it in your password manager.
- The Pages entry point accepts only `tinydreams.pages.dev` (and `localhost` for isolated QA). Preview aliases return 404, preventing retired deployments from exposing earlier password configurations. Changing the public hostname requires updating that allowlist and rebuilding. Preview deployments have separate environment settings. Do not bind personal production D1 to untrusted preview code. Old deployments that still run the Access-based build remain closed without its configuration. Delete obsolete public deployments when retiring them; changing variables does not rewrite past deployments.

Future multi-user invitations require a separate identity model; do not share this owner password or broaden the `local-preview` mapping.

References: https://developers.cloudflare.com/pages/get-started/direct-upload/ and https://developers.cloudflare.com/pages/functions/bindings/#secrets

## Home Screen icon

The app and login page declare a 180px Apple touch PNG. The manifest also includes 192px and 512px PNGs. Icons are opaque rasterizations of the existing `assets/icon.svg`, not a new logo. Installation metadata is available without a session so iOS can fetch it independently; personal artwork and APIs remain protected. After deploying this update, remove the old Home Screen shortcut and add the site again from Safari to refresh the cached icon.

## Automatic updates

Each build computes a stable content fingerprint from app code, styles, artwork and Pages authentication/entry code. HTML, CSS resource URLs and manifest icons include this version. Rebuilding identical contents preserves the version. `/version.json` and `/updates.js` are public installation metadata with `Cache-Control: no-store`; all authenticated app responses are also private/no-store. No service worker or offline cache is installed, and no user storage/cookies are cleared.

An open app checks the current release every minute while visible and when returning, restoring a page or reconnecting. A changed version triggers a single reload after a short idle interval, deferred while a dialog, editable field or app write is active. Network failures keep the current working page. A changed deployment cannot update an OS-suspended web app until it resumes and has network access.

Publish this release and open/reload it once to install the checker in the running page; older already-open pages do not have that code. Subsequent releases update automatically. Browser UI/installed Home Screen icon caches are managed separately by iOS, so a deliberately changed app icon may still require recreating the shortcut.

`npm test` includes update lifecycle tests. `node scripts/check-updates-browser.mjs` uses offline QA/CDP and a simulated release, without production writes, to check draft preservation and idle reload.
